# WK-HOME-01 — production W/K on HomeBridge

## Intent

**Problem.** The production browser surface still runs the legacy per-profile `/voice-session` transport, whose upstream listeners are gone, so `/state` closes `1011` and the household sees a silent "disconnected". The supported path for W/K (`Puck, Touch and shared W/K browser room surfaces use HomeBridge in this release`, `course-correction-2026-09-23.md:17`) exists in code but is opt-in, is not what is deployed, and cannot yet be run in production: it needs a static operator-minted conversation handle that Home retires, one Profile per process, and a credential file that never renews.

**Approach.** Pair the appliance with Home once as one Device holding grants for every Home-authorized Profile, with later exact grants added through Home administration without re-pairing. There is no separate browser sign-in: anyone who can reach the page can use those authorized Profiles. The current Home grant list drives a Profile selector; optional local wake phrases are shortcuts, not an allow-list. Each browser tab gets an independent claim and conversation; page/socket and bridge reconnects begin fresh conversations with no prompt replay. Add an honest unavailable state, a Home-admission health signal, and Ops evidence without claiming unmeasured idle Hermes health. Switch the managed deployment to Home, bake for 24 hours, then hand off R7 legacy removal to its separate owner.

**Success.** `WK-1` and `WK-2` can be accepted on the supported path: two real browsers (Mac Chrome and iPad Safari) hold independent Home conversations through the deployed appliance, Home and active Hermes failures show an honest reason, and nothing in the managed deployment depends on a modified agent or `voice-*.example.com` gateways. The original monitoring obligations remain distinct **OPEN acceptance dependencies**: a pre-expiry `credential_expiring` signal and a traffic-free Grafana `probe_success` alert for Home admission; idle Hermes outage visibility within minutes is a separate gap. The checked-in Home dashboards do not evidence idle Standard readiness, H5 is unapproved, and S7 cannot claim these requirements until existing approved evidence is identified and demonstrated or any missing source is separately authorized.

### What `HomeBrowserSession` and the Home transport do today [FACT]

- **Selection is fail-closed.** `--browser-transport home` needs `--browser-voice`, an exact `wss://…/api/v1/bridge/ws` URL, a Device credential and a conversation handle; the process refuses to start without them and never falls back to a bearer profile (`appliance.py:1902-1935,2382-2394`; `puck_bridge/home_session.py:144-162`).
- **One static handle, shared by every browser.** `_create_browser_session` builds a fresh `HomeBrowserSession(url, credential, handle)` per socket but passes the same configured handle to all of them (`appliance.py:1997-1999`). STD-8 deferred exactly this question: "Define whether independent Home browser bindings may reuse one opaque handle and durable Standard Session while preserving concurrent W/K session isolation" (`deferred-work.md:266-270`; `spec-standard-8-…md:183`). **UNKNOWN** whether Home accepts two concurrent `conversation.open` calls on one handle; Home's claim store binds one claim to one Standard Session (`HOME-NW-17` spec `:54`; Home `production.py:296-306`), so the WK-2 isolation guarantee cannot be assumed.
- **Handle lifetime does not fit an appliance.** A claim that is never opened expires after 90 s (`production.py:52`, `NW-17 spec :53`). A wake or tap claim also ends 8 s after playback (`HOME-NW-16 spec :26`). An operator-minted handle in an env file is therefore a disposable test input, not a service credential. [INFERENCE] a restart, an idle hour or a Home restart (which closes every claim, `validation-home-mig-09-readiness.md:189`) leaves the appliance with a dead handle.
- **One Profile per process.** In Home mode `candidates = [self._active_profile]` (`appliance.py:2008-2009`), `_switch_profile` returns `False` ("Home owns browser profile routing", `:2167-2169`), and `route_profile` keeps the wake phrase only as a gate; it never selects a different conversation (`:2229-2257`). The three-phrase catalog (`hey missy`/`hey skippy`/`hey spark`) that production advertises is therefore not honoured by Home mode.
- **Credential never renews.** The Device credential is read from a file or env var once (`appliance.py:355-363,1914-1920`). Home credentials last 90 days and renew inside a 14-day window (Home `credentials.py:34-35`; TUI client renew logic at `home_client.py:335-350`). [INFERENCE] a static file credential stops working after 90 days with no warning.
- **Auth shape.** `Authorization: Device <credential>` on the bridge (`home_session.py:182`); the browser never sees it (`STD-8 spec :56-58`).
- **Capacity.** Admission is reserved per socket before any upstream work; at the cap the socket closes `1013 "browser session capacity reached"` and the page shows "All browser sessions are busy — retrying" (`server.py:48-53,693-701,1018-1025`; `web/src/state/channel.ts:151`; `web/src/surfaces/StateSurface.svelte:41-42`). Cap is `--display-max-browser-sessions`, default 8 (`appliance.py:3003-3009`).
- **Failure today.** A factory error closes the socket `1011 "browser session unavailable"` after logging only the exception type (`server.py:869-875`, PR #225; `appliance.py:2063-2085`). The page cannot tell this from any other close: every non-`1013` close renders "Display disconnected — check the host connection" (`channel.ts:151`; `StateSurface.svelte:29`; `App.svelte:203-210`). The reason string is not read.
- **No deep health.** `DisplayServer` serves `/state`, `/action` and static files only (`server.py:540-610`). The deploy smoke check requires a first snapshot (`scripts/check_ops_web.py:129-176`). [INFERENCE] in browser-context mode that snapshot is only sent after the upstream session connects (`appliance.py:2044-2053,2078-2086`; `server.py:750-754,869-875`), so a deploy while upstream is down fails the smoke check and rolls back (`deploy_ops_web.sh:1023-1063`).
- **Touch already uses claims, browser does not.** `TouchDoorway` claims over HTTP on the first `mic_start` and never holds a session before then (`appliance.py:2111-2144`; `touch.py:1-21,222-286`). `--touch-voice` and `--browser-voice` are mutually exclusive in one process (`appliance.py:2349-2354`).

### What Home offers [FACT]

- **Personal-client admission already exists and is deployed to the tailnet.** `POST /api/v1/client-claims` takes a paired Device and one of its `grant_id`s and returns an opaque handle; session choice `new`/`most_recent`/`resume`; no Room, no arbitration, no idle timer; per-device limit 8; reconnect grace 120 s; revoke closes claims (`HOME-NW-17 spec :51-57,97-148`; `production.py:246-348`). The route is among the paths Serve publishes (`hermes-relay-home/deploy/windows/README.md:316-319`).
- **`HOME-NW-18`** adds `GET /api/v1/client-claims` and `POST /api/v1/client-claims/close` so a device can list and release its own claims, written after an iPad refusal loop created seven unopened claims in 19 s and hit `claim_limit` (`HOME-NW-18 spec :23`).
- **The client kinds that may hold `client_claim` are `tui`, `ios`, `macos`, `android`** (`credentials.py:39,609-611`). A `client_claim` credential cannot also carry `wake_claim` or `touch_claim` (`:604-608`). There is no browser or display kind.
- **Pairing requires `secure_storage == "platform_secure_store"`** (`credentials.py:38,407,678`). The TUI refuses to pair without macOS Keychain or Linux Secret Service (`home_client.py:145-160`; `README.md:102`).
- **Owned Profiles need owner approval.** A grant to an owned Profile that another live device already holds is `pending_owner` until a holder approves it (`credentials.py:1180-1215`; `NW-17 spec :48`). Any device holding an active grant for the Profile can approve others, with no device-type check (`credentials.py:1029-1062`).
- **Device capabilities are deny-by-default.** `sensitive_entry` and `consequence_confirm` must be granted in both credential scope and device configuration (`HOME-NW-10 spec :20,41-50`). The browser UI cannot collect secret/sudo values (`docs/ops-web-deployment.md:35-38`).
- **Health read exists but is Room-bound.** `GET /api/v1/devices/{id}/health` reports route, authorization, bridge and Standard readiness without opening a conversation, but needs `health_view` and a target device whose `room_id` is in the caller's scope rooms (Home `application.py:695-736`; `HOME-NW-09 spec :19-27`). A client device has `rooms: []` (`NW-17 spec :78`). **UNKNOWN** whether a client device appears in `configuration["devices"]` at all.
- **Home has no browser-admission story.** No browser, display or W/K kind appears in `src/hermes_home` (grep of the repository for `browser`/`kiosk` returns only an Origin check at `api/pairing.py:427`).

## Target design

### 1. Admission model (Q3, Q4, Q5)

- **APPROVED 2026-10-08:** pair one appliance Device once, not one Device per browser. That Device may use every Profile Home authorizes for it, including later grants; this is a policy outcome, not a hard-coded catalog. Browsers hold no Home credential. There is no separate browser sign-in: anyone who reaches the page may use those authorized Profiles. Access is household Tailscale only, never public, and is a network boundary rather than per-user authentication.
- **PROPOSED H1 Home change** (draft Home stub `HOME-NW-17-browser-admission`): add a `browser` endpoint kind that may hold `client_claim`; keep `sensitive_entry`/`consequence_confirm` omitted. **APPROVED H2, 2026-10-08:** the appliance/browser device cannot approve or reject other devices' access; approvals remain in existing Home administration tools. **APPROVED H3/Q5, 2026-10-08:** the appliance pairing credential is persisted in a private server-side file readable only by the service account and administrators, survives restarts, and never enters browser storage, logs, or the repository. `service_private_file` attestation applies only to this browser appliance; every other device retains its existing secure-store requirement. These approvals do not approve H1, H5, or implementation/deployment.
- **Pairing and later grants.** Pair the appliance once through Home. A Home administrator adds any later Profile grant through the proposed exact, append-only Home-admin operation in Home H6; owned grants use Home's existing authorization/owner-approval path. No re-pair, wildcard grant, or grant approval by the appliance. Home acceptance owns the Home-side contract; this spec owns the appliance, browser, and deployment integration.
- **Credential persistence/renewal (PROPOSED mechanics).** Use a private server file with restrictive service/admin access, durable across releases/restarts; never put the credential in YAML, a unit file, URL, log, browser bundle, or repository. The opaque `grant_id` is not a credential and may be persisted only in the existing local `home_grant` field when a wake shortcut needs a stable binding; do not commit production grant IDs to the repository, log them, expose them to the browser, or send them over HomeBridge. Serialize renewal across tabs/processes; persist one idempotent renewal request ID before contacting Home, retry only that same renewal if the response or final save is uncertain, and publish a new credential only after it is durably saved. Home renewal closes old-generation claims: retire those claims, mark in-flight turns uncertain, discard stale handles, and permit only a later explicit user action to create a fresh claim. Never replay a turn or call this revocation/re-pairing unless Home actually rejects the credential. Exact path, permissions, atomic-write/locking mechanism, renewal schedule, and degraded-state details remain proposals, not implementation approval.

### 2. Profile mapping (Q6, Q7)

- **APPROVED Q6, 2026-10-08:** all Profiles Home authorizes for this appliance are in scope, including new ones once granted; do not hardcode the current three. Home's latest device-configuration `client_grants` is the source of truth. The browser displays every active/available grant in a Profile selector regardless of whether it has a local wake phrase; local catalog entries are optional wake shortcuts only, not an authorization allow-list or a prerequisite for discovery.
- **PROPOSED bounded refresh:** load Home grants at appliance start and maintain a maximum 30-second snapshot age while pages are connected; refresh before any new claim if the snapshot is older. A newly approved grant becomes selectable by the next refresh. Keep Home `grant_id` as the adapter-side selector identity; send it only on the Home HTTP claim route and never across HomeBridge.
- **PROPOSED durable shortcut binding and label safety:** labels are display-only, never identity. Persist the exact grant ID in the existing local `home_grant` shortcut mapping and resolve shortcuts only by that ID, never by matching a display label. A rename updates the displayed label while the same grant ID stays bound; revocation/re-issuance produces a different ID and leaves the old shortcut unresolved until an operator deliberately rebinds it. A legacy label-only shortcut remains unresolved until explicitly rebound; do not auto-match it to the current label. The general selector still exposes every current authorized grant, including unmapped Profiles. Home rejects duplicate current per-device labels; if a legacy collision is returned, suppress ambiguous routing/selection rather than choose arbitrarily. Reusing a label after a rename/revocation can never redirect an old ID-bound shortcut.
- A grant that is pending, revoked, or unavailable is reported unavailable for that Profile only; other usable grants continue working. Switching while idle closes/reconciles the old claim before a new one; during an active turn retain the existing `active_turn` rejection (`appliance.py:2246-2253,2264-2300`).
- Wake phrases remain appliance-local configuration; Home-owned custom wake phrases are `HOME-NW-13`, `backlog`, `scope-decision` (`validation-home-mig-09-readiness.md:96`). The Home-mode validator may validate optional local shortcuts but must not require a fixed Profile set or three phrases.
- On `stale_configuration`, refresh the grant snapshot once and show a typed configuration-changed state; require a new deliberate user action. Do not retry the claim or replay the associated action automatically, even if the stale response means no turn was admitted.

### 3. Per-connection lifecycle (Q8, Q9)

1. **Startup gate (PROPOSED).** Before browser admissions, use NW-18's authenticated HTTP `GET /api/v1/client-claims` and `POST /api/v1/client-claims/close` with the current Device credential to list this Device's claims and close only claims left from the previous process. Make one bounded reconciliation pass. Release a claim from accounting only after Home confirms it absent or confirms close; retain unconfirmed claims as tombstones. If Home is unreachable or the remaining safe claim budget cannot be established after counting those tombstones, remain visibly unavailable; never admit as though an unconfirmed claim were gone.
2. **Accept socket.** Reserve the existing local browser slot and preserve `1013` for that local socket cap. Do not create a Home claim yet.
3. **Preflight.** Renew if due, fetch the current configuration revision and grants, and populate the dynamic selector. Preflight creates no claim or Standard session. Home/authentication errors publish the typed unavailable state.
4. **First user turn.** Refresh configuration if its bounded cache expired; verify the selected grant is currently active/available and make exactly one claim with `session: {mode: "new"}` before `conversation.open`. Never use `most_recent` or `resume`. A `stale_configuration` response triggers the one refresh/display update above, not a second claim attempt.
5. **Close/reconnect.** On browser leave or bridge loss, cancel the turn, mark any in-flight result uncertain, discard its conversational handle, and attempt `conversation.close` only on the already-bound healthy bridge connection. If the bridge is lost or close is unconfirmed, retain a tombstone and reconcile with NW-18's authenticated HTTP claim-list/close routes using the current Device credential. Do not open an unbound control-only bridge connection: the existing bridge has no claim-list method and close requires a bound handle. The first later conversational action after either browser-page or bridge reconnect receives a new claim and fresh Standard conversation.
6. **Credential renewal.** Serialize renewal across all tabs/processes. Before requesting renewal, block new claims and transition current tabs out of conversational work; mark in-flight turns uncertain and do not replay them. Durably store one idempotent request ID before the Home request. If its response or credential save is uncertain, retain that ID and reconcile by repeating only that renewal request; treat old-generation claims as possibly invalid, close/reconcile them, and discard their references. Do not start claims with a credential known or possibly stale. After the new credential is durably saved, a later explicit user action creates a fresh claim. Distinguish actual revocation from renewal uncertainty; neither case replays a turn.
7. **One attempt per user action.** Never automatically retry a client claim, conversation open, or user action after stale configuration, uncertainty, or transport failure. The NW-18 refusal loop is the precedent (`HOME-NW-18 spec :23`).

**PROPOSED** rationale for claim-at-first-turn: idle pages hold no Home claim or Standard session, and the 90 s first-open expiry cannot leak slots. Cost: first-turn latency is **UNKNOWN** until measured.

### 4. Capacity and `1013` (Q10, E1)

- `1013` keeps one meaning: the appliance's local browser-socket cap (`server.py:693-701`). Default 8 is only a proposed ceiling and must be no greater than Home's actual per-device claim limit before rollout; Home does not expose that limit to the device (**UNKNOWN**).
- Home claim usage is not guaranteed to be at most the number of live browser sockets. Count every active claim and every close-pending/unconfirmed tombstone against the safe local claim budget until Home confirms it absent/closed. Do not release capacity on socket departure alone. A list/close reconciliation may release an orphan, but must never close a claim owned by another live tab.
- If Home returns `claim_limit`, or a local limit is exhausted by unresolved claims, report typed `claim_limit` and do not retry automatically. Keep this distinct from local `1013`; one user action produces at most one claim attempt.

### 5. No-replay reconnect

**APPROVED Q9, 2026-10-08:** a browser page reload/socket reconnect and a HomeBridge transport reconnect both begin a fresh conversation; tabs are independent and no prior prompt or uncertain turn is replayed. **PROPOSED mechanics:** use only `session: {mode: "new"}` for conversational work and never call `conversation.reconnect`, `most_recent`, or `resume` to preserve an old conversation. Claim cleanup after bridge loss uses only NW-18 authenticated HTTP list/close; there is no unbound control-only bridge connection. The first post-reconnect user action starts a new claim/conversation; it cannot silently continue the old one.

### 6. Honest "unavailable" (Q11)

Allowlisted reason tokens, produced by the appliance from typed errors, never from upstream text:

| Token | Meaning | User-visible sentence (PROPOSED) |
|---|---|---|
| `home_unreachable` | TCP/TLS/timeout/5xx talking to Home (`home_client.py` `transport`, `service_unavailable`) | "Hermes Home can't be reached. Retrying." |
| `home_unauthorized` | Credential revoked, expired or rejected (`unauthorized`) | "This display needs to be paired again." |
| `hermes_unavailable` | Home is up but its Standard Hermes is not (Home bridge status `unavailable`/`hermes_unavailable`, Home `bridge/endpoint.py:972,173-183`) | "Hermes isn't responding. Retrying." |
| `profile_unavailable` / `grant_pending` | Per-Profile grant not usable | "<Name> isn't available on this display." |
| `configuration_changed` | Home returns `stale_configuration`; the refreshed Profile/grant must be reviewed before another claim | "Home access changed. Review the Profile and try again." |
| `credential_renewal_uncertain` | Home may have renewed but the private-file save/response is not yet confirmed; no new claim may use stale material | "Home access is being recovered. This conversation was not replayed." |
| `claim_limit` | Home's per-device limit | "Too many conversations are open. Try again in a moment." |
| `at_capacity` | Existing `1013` | existing text (`StateSurface.svelte:41-42`) |

- **Delivery.** Close code stays `1011` for unavailable; the close reason carries the token (a WebSocket close reason allows 123 bytes). `channel.ts` reads `event.reason`; an unknown token falls back to today's generic text. A turn-time failure publishes a snapshot with `status_text` instead of closing.
- **Server logs.** One structured line per failed admission: `browser.admission.failed reason=<token> exc=<type> connection=<short id>`, at WARNING (unavailable) or ERROR (`home_unauthorized`), rate-limited per reason. No credential, handle, `grant_id`, `claim_ref`, URL or upstream message is ever logged (`HOME-NW-18 spec :37` forbids logging these identifiers on the Home side; the appliance follows the same rule). This extends PR #225, which logs only the exception type (`server.py:869-872`; `appliance.py:2065-2084`).

### 7. Ops-observable health (Q12, A6)

- **PROPOSED `GET /healthz`** is a tailnet-only, non-mutating Home-admission signal: cached Home reachability, credential state/renewal, and at least one currently usable grant; `200 {"status":"ok"}` or `503 {"status":"degraded","reason":"<token>"}`. It creates no claim/session and does not claim to report Standard readiness. This endpoint alone has no Origin requirement because it is non-mutating; do not extend that exception to WebSocket `/state` or POST `/action`.
- **PROPOSED/open evidence requirement:** preserve the traffic-free tailnet blackbox probe of `/healthz` and Grafana `probe_success` alert for Home admission, plus the pre-expiry `credential_expiring` signal. These must be demonstrable without a browser connection. Whether Ops has the exporter, alert, or pre-expiry signal/wiring remains **UNKNOWN**; if any is absent, the corresponding S7 acceptance stays open pending existing approved evidence or a separate approval. This document does not authorize new monitoring.
- **Idle Hermes readiness remains a separate open evidence gap.** The checked-in Home metrics and Grafana dashboards contain no Standard-readiness signal. Home's existing device-health route requires `health_view` and a Room-scoped target; a browser Device has no Room. Optional Home H5 (self-health/`health_view`) is **not approved**, and neither H5 nor new monitoring is authorized here. Typed `hermes_unavailable` covers an observed active admission/turn failure only; it does not prove idle-outage detection. S7 cannot claim the original Grafana-within-minutes Hermes-health promise until an existing approved signal is identified and demonstrated, or an owner separately approves a source/capability.

## Acceptance criteria

Not accepted until the real-browser rows have dated evidence from the named build. Fake-bridge runs are evidence of code behaviour only (`STD-8 spec :67-68`).

- **AC-1 Pairing and credential.** Pair the appliance once. Verify the approved `service_private_file` attestation is browser-appliance-only in Home's enrollment and consume path, while other device kinds retain current secure-store behavior (Home contract evidence). In the TUI appliance, persist the credential in a private server-side file readable only by service account/admins across restart; never put it in YAML, logs, repository, URL, unit file, or browser bundle. An opaque `grant_id` may appear only in the existing local `home_grant` field to bind an optional wake shortcut; it is not credential material, is never logged/exposed to the browser/sent over HomeBridge, and production grant IDs are not committed to the repository. Home revocation makes the next admission show `home_unauthorized`. No browser sign-in; anyone within the household tailnet boundary can use authorized Profiles.
- **AC-2 Per-connection isolation.** Two tabs hold independent claims and Standard conversations; overlapping turns, prompts, and audio stay with their owner. A tab leaving closes/reconciles only its claim and never closes another live tab's claim.
- **AC-3 Dynamic Profile access.** The visible selector reflects every current Home-authorized active grant, including a new Profile granted after pairing and a grant with no local wake mapping; newly approved grants appear by the next bounded refresh. Exercise optional wake routing separately by stable grant ID. Rename a Profile label and verify the shortcut remains bound to that same grant ID; revoke/re-issue it and reuse the former label for another Profile, then verify the old shortcut is unresolved rather than routed elsewhere. A legacy label-only mapping remains unresolved until explicitly rebound. Force duplicate current labels and verify they are rejected/ambiguous rather than arbitrarily routed. Verify post-pair grant uses the Home-admin/owner path without re-pairing or browser approval, unavailable/revoked grants do not disable other Profiles, and no Profile ID or grant ID crosses HomeBridge.
- **AC-4 Fresh conversations/no replay.** Exercise page reload, browser socket reconnect, HomeBridge reconnect, and two independent tabs. Each reconnect's first conversational action uses a fresh `new` claim/session; no old prompt or uncertain turn is resent and no `conversation.reconnect` occurs. After bridge loss, use only NW-18 authenticated HTTP list/close for old claims; never create an unbound control-only bridge connection.

## Risks

- **R1 Static-handle cutover regression.** Per-connection claims remove the shared-handle dependency; if S3 fails to replace the static handle, isolation remains unproven (`deferred-work.md:266-270`).
- **R2 Owner-approver exposure.** A shared display holding an owned Profile must not approve or reject another device's grant (`credentials.py:1029-1062`). Mitigation requires Home's direct mutation-boundary guard and negative API/domain tests, not only filtering pending-grant listings.
- **R3 Credential renewal uncertainty.** Credentials last 90 days with a 14-day renewal window (`credentials.py:34-35`); an uncertain response/save can invalidate old-generation claims. Mitigation is S2 serialized renewal with a durable idempotency ID and no turn replay; exact mechanics remain proposed.
- **R4 Claim leakage and refusal loops.** Seven unopened claims hit the limit in 19 s on iOS (`HOME-NW-18 spec :23`). Mitigate with lazy claims, one attempt per user action, bounded startup sweep, tombstones for unconfirmed close, and no admission beyond known safe capacity.
- **R5 Reachability from Ops to Home.** Tailnet grant and Serve route from Ops are **UNKNOWN**; verify before rollout (`deploy/windows/README.md:316-319`).
- **R6 Home/Hermes outage visibility.** Home-admission outage is visible via proposed `/healthz`; active Hermes failure can be reported on a turn. Idle Hermes health is not measured by checked-in Home dashboards and remains an open evidence/approval dependency.
- **R7 Deploy-time rollback loop.** A Home-down smoke must not roll the first Home release back to the dead legacy product. Separate package/deployment success from Home health; use a known compatible Home build or safe unavailable state.
- **R8 Network boundary, not browser identity.** No separate browser sign-in exists: anyone reaching the page can use the appliance's Home-authorized Profiles. Tailscale is the only access path; public access and direct proxy/backend bypass are prohibited. Preserve Origin checks separately from this network boundary.
- **R9 Touch claim payload mismatch (separate finding, not fixed here).** `HttpTouchClaimClient` sends `config_revision` (string) and `observed_at` (ISO string) (`touch.py:241-249`); Home's `_touch_claim_values` requires an integer `configuration_revision` and `initiation: {kind, observed_at_ms}` (Home `application.py:2427-2441`). [INFERENCE] a real Home rejects the current Touch claim. STD-7 notes `HttpTouchClaimClient._post` lacks a test (`spec-standard-7-esp32-touch-audio-session-adapter.md:193`). Recommend a separate ticket.
- **R10 Second appliance on Ops.** A developer copy of `home_display.appliance` runs on Ops against the dead `:8792` [OPS]; it is outside this spec and Ops should decide whether to stop it.
- **R11 First-turn latency** from claim-at-first-turn is unmeasured (UNKNOWN).
