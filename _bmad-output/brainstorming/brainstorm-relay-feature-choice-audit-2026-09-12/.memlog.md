- (direction by user) Evaluate potential features one by one; do not assume the existing product's choices are automatically better.
- (finding by coach) Brainstorm log was reconstructed after workspace cleanup; decisions below reflect the discussion already completed.
- (decision by user) Roaming clients should switch endpoints automatically; route order is home network first, Tailscale second, public internet only when explicitly configured.
- (decision by user) Laptop and phones use QR pairing; the display shows a QR code that a phone scans and approves. Home issues a limited device credential rather than a personal Hermes token.
- (decision by user) Displays can access all household profiles through different wake words. Home owns the wake-word-to-profile mapping and credentials.
- (decision by user) A selected profile stays attached across continuous follow-up turns while the conversation is active; a later wake after the conversation ends starts fresh.
- (decision by user) TUI and phones may request broader Hermes tools with explicit approval; displays are limited to a small set of household actions.
- (decision by user) Tool permissions are divided by category rather than one all-tools switch; risky actions require confirmation.
- (decision by user) Hermes may send proactive notifications when no conversation is active, with per-device opt-in, categories, quiet hours, and privacy controls.
- (decision by user) Displays may receive proactive notifications, but only household-safe alerts; personal notifications belong on phones or laptops.
- (decision by user) Phones and laptops may reply from notifications; displays use fixed buttons only.
- (decision by user) One household Hermes server is enough; do not add multiple separate server connections as a product feature now.
- (idea by coach) Next candidate: file and image attachments. The current TUI can stage local images but the direct relay channel remains text-only; standard Hermes surfaces support attachments.
- (finding by coach) The current TUI already has image-only staging, metadata validation, path completion, and an honest unsupported-attachment stop. A real attachment feature should add an upload/attachment reference path rather than put file bytes into the voice WebSocket.
- (question by coach) Should attachment support start with images only, or support arbitrary files from the beginning?
