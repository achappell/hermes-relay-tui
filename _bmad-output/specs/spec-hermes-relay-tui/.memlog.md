- (capability) CAP-1: An authorized Puck or Client can start a turn for a selected Hermes Profile, with the profile fixed before Puck capture.
- (capability) CAP-2: Each doorway exposes honest capture, processing, audio, completion, and unavailable phases, and delivers the Hermes response without local paraphrase or fallback.
- (capability) CAP-3: After a Puck response, the doorway supports an eight-second wake-free follow-up; exact stop closes capture silently, and reconnect never replays an uncertain turn.
- (capability) CAP-4: The platform enforces unique wake mappings, individually authorized Devices, fail-closed unavailable identities, and one winning Device when several hear a wake.
- (capability) CAP-5: Room Displays and the iPad kiosk render a shared ambient/turn/recovery contract, mirror only the owning Room's active conversation, and show voice-only Hermes prompts without touch response actions.
- (capability) CAP-6: Displays promote a consistent visual Departure Card from qualifying shared-calendar events and return to ambient content when the event no longer qualifies.
- (capability) CAP-7: iOS can discover, approve, configure, and revoke physical Devices, with explicit Room and Wake Mapping setup and re-enrollment after revocation.
- (capability) CAP-8: iOS and the TUI provide independent Hermes conversation doorways with intentional local history, while the TUI's diagnostics remain an engineering capability.
- (constraint) Hermes remains authoritative for profile context, answer content, correctness, calendar, household home, and travel estimates; doorways route, present, and report state.
- (constraint) Core session/protocol and portable display rules remain framework-independent; front ends consume SessionProtocol and the shared display contract rather than duplicating policy.
- (constraint) Active response text and prompts are Room-local; only an explicitly defined visual Departure Card propagates household-wide.
- (constraint) Puck audio is transient and home-LAN-only; the Media Server is not a transcript archive, and only intentional iOS/TUI history may persist by default.
- (constraint) Every physical Device has an individual revocable credential, and unapproved, revoked, or unavailable identity fails closed before capture.
- (constraint) The first release is a single-Room pilot using the ReSpeaker-based Puck prototype, ESP32-S3/LVGL Display, iPad browser kiosk, iOS/macOS Client boundary, and TUI; contracts remain multi-Room-ready.
- (constraint) Supported surfaces must keep the named phase semantics truthful, with roughly one-second wake acknowledgement and roughly four-second first spoken audio as v1 working targets.
- (constraint) The private pilot trusts an explicitly enabled home-LAN display binding; credentials never cross snapshots, actions, diagnostics, browser state, or display transport.
- (decision) Version one does not host Hermes intelligence locally, become a general smart-home platform, or create a second assistant identity.
- (decision) Version one excludes touch-based Hermes prompt choices, audible Departure Cards, active-playback barge-in before an echo-safe route, full response text on the Puck TFT, default shared-device transcript archives, and a native iPad Display application.
- (decision) Multi-room hardware rollout, public provisioning/commercial deployment, speculative repository splitting, and a diagnostic-first TUI experience are outside the first release.
- (assumption) The initial private-pilot success threshold is four successful UJ-1 dinner journeys out of five scripted attempts; the PRD marks this threshold provisional.

- (decision) Story 1 resolved: the Puck's on-device wake-word engine is ESPHome's `micro_wake_word` component, adopting Seeed's own reSpeaker Lite firmware reference for this exact board over Espressif ESP-SR or a from-scratch port. This de-risks story 2 (firmware bring-up) against a known-working hardware/software combination, and ESPHome's Assist Satellite architecture already solves WiFi provisioning and wake-then-stream-to-host audio, which stories 4 and 5 would otherwise build from nothing. `micro_wake_word` v2 also runs several independently-trained models concurrently and reports which one fired, directly serving FR7 (multiple Wake Mappings per Device); per-phrase training effort (Piper TTS synthetic samples through `OHF-Voice/micro-wake-word`/`alfiedennen/microwakeword-trainer`, the same conceptual approach as `hey_hermes.onnx`) is the real cost of adding each Wake Mapping, not a platform limit.
- (decision) Explicitly ruled out: sherpa-onnx, the open-vocabulary engine previously used for flexible host-side wake words. Its million-parameter streaming-ASR-transducer KWS models target embedded Linux/mobile-class hardware (Raspberry Pi, Android, RISC-V boards), not a bare-metal, OS-less, MMU-less microcontroller like the XIAO ESP32-S3; it does not run on-device on the Puck.
- (decision) Consequence recorded plainly: the existing `hey_hermes.onnx` model does not carry over as-is — `micro_wake_word` uses its own model format, so keeping the "hey hermes" phrase means retraining it for that pipeline, not reusing the current file. The host-side `wake.py`/`wakewords/*.onnx` stack (HOME-05's appliance path) is untouched by this story.
