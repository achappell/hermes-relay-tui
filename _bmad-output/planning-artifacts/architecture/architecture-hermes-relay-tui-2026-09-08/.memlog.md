- (question) Load-bearing paradigm choice: compare hexagonal ports-and-adapters with a functional-core/imperative-shell emphasis against a conventional layered monolith and against independently-owned front-end stacks. The spine must choose the model that keeps protocol/session rules and shared display rules canonical while allowing TUI, appliance, native LVGL, and Web/WASM to evolve independently.
- (decision) [ADOPTED] Use ports-and-adapters as the repository paradigm, with functional cores at two seams: the UI-framework-free Python Hermes session/protocol core and the portable C shared-display reducer. This binds all front ends to consume canonical core contracts and prevents protocol, turn-state, and display-rule duplication across TUI, appliance, ESP/native simulator, and Web/WASM targets.
- (decision) [ADOPTED] State ownership is singular by domain: HermesSession owns connection, capabilities, and active-turn protocol facts; each front-end coordinator owns its local device lifecycle and maps events into its own published snapshot; shared/display owns reducer-accepted view, stale-sequence rejection, and action validation; DisplayStatePublisher owns only the latest immutable transport snapshot and sequence; drafts, queues, presentation state, and optional local history remain surface-local, and appliance/display paths do not archive transcripts. This prevents competing mutable owners and accidental transcript fan-out or persistence.
- (decision) [ADOPTED] Use a contract-first compatibility boundary: versioned DisplaySnapshot and DisplayAction JSON schemas plus executable fixtures define cross-target shapes; the portable C reducer owns bounded display semantics and adapters conform independently. Additive unknown fields are ignored, malformed known fields are rejected, sequence is monotonic per channel with stale snapshots non-mutating, actions are capability- and reducer-validated, and schema versions change only for semantic breaks. This prevents language/toolchain coupling and semantic drift between Python, C, TypeScript, ESP, and WASM targets.
- (decision) [ADOPTED] Deploy as independent doorway processes with local state: hermes-relay TUI, hermes-relay-home appliance/display host, and display clients (Web/WASM or ESP/native) connected over the local display channel. Hermes remains the external session/model/speech authority; this repository adds no shared household database, broker, or transcript store. Reconnect is per process and never replays an unconfirmed turn. This prevents premature centralization and cross-process ownership ambiguity.
- (decision) [ADOPTED] Credential and privacy boundary: Hermes bearer tokens remain only in the owning local process/profile and never cross display snapshots, action payloads, or diagnostics; display state carries bounded, non-secret data. The display server binds loopback by default, and remote LAN binding requires explicit opt-in. The private-pilot LAN is an explicit trust assumption; per-device authentication, encrypted display transport, provisioning, and revocation are deferred until device identity exists. This prevents accidental secret propagation and prevents the spine from misrepresenting the pilot channel as production security.
- (constraint) [ADOPTED] Lifecycle and recovery are explicit: blocking microphone/audio work stays off UI event loops; shutdown cancels active capture and turn workers before releasing devices; connection loss is visible; reconnects are bounded; a turn that may have reached Hermes is never replayed; recovery never silently reopens capture or resubmits a pending turn. This prevents duplicate turns, stuck thinking states, leaked audio ownership, and UI freezes.
- (decision) [ADOPTED] Keep front-end dependencies isolated: the base Python install contains the TUI/core path, voice and wake stacks remain optional extras, and each front end keeps its own entry point/build environment. Keep one repository until a demonstrated dependency conflict makes a separate hermes-relay-core package cheaper. This prevents speculative repository splits and accidental hardware dependency drag.
- (decision) [ADOPTED] Shared-contract changes require executable conformance evidence: update schema and fixtures together, run Python contract tests, portable/native C reducer tests, Web/TypeScript parser or reducer tests, and target adapter tests; enforce core/UI separation with the import-boundary test. This prevents a contract change from passing in one target while another silently interprets it differently.
